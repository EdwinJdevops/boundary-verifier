# EXP-001 — Declared vs effective isolation

## Purpose

Falsify or support one narrow thesis:

> Direct containment controls can hold while an allowed intermediary creates an effective communication path that violates a declared workload boundary.

The lab will intentionally create this condition. A successful experiment demonstrates only that the verifier can identify a seeded composition failure. It does not establish product differentiation.

## Ground truth

Two Kubernetes namespaces represent isolated tenants:

- `tenant-a`
- `tenant-b`

A third namespace, `shared-services`, contains a deliberately shared mutable service used only by the lab.

Expected direct controls:

1. tenant-a -> tenant-b: blocked.
2. tenant-b -> tenant-a: blocked.
3. tenant-a -> arbitrary external destination: blocked.
4. tenant-a -> explicitly allowed shared lab service: allowed.

Seeded forbidden effective path:

```
tenant-a
  -> shared-services/canary-store
  -> shared mutable canary
  -> tenant-b
```

The shared service is deliberately designed into the experiment. It is not presented as a vulnerability in Kubernetes or any vendor.

## Acceptance criteria

EXP-001 passes its engineering milestone only if all are reproducible:

- direct A -> B probe is blocked;
- direct B -> A probe is blocked;
- A can write a random, per-run canary through the explicitly allowed shared service;
- B can observe that exact canary without direct A -> B connectivity;
- evidence identifies the intermediary path rather than emitting only a generic alert;
- each run has a unique run ID and canary value;
- negative results are represented as OBSERVED_BLOCKED, UNKNOWN, or NOT_EVALUATED rather than overstated as proof of isolation.

## Product falsification gate

After the harness is stable, run established baseline tooling against the exact same scenarios. If established tooling exposes every meaningful seeded path with comparable deployment effort, reproducibility, and path evidence, the differentiated product thesis fails.

## Explicitly deferred

- managed cloud agent runtimes;
- IAM/token-exchange reachability;
- metadata-service paths;
- DNS covert channels;
- arbitrary timing/covert channels;
- eBPF instrumentation;
- UI/dashboard;
- remediation;
- autonomous exploitation.

Those are not required to answer EXP-001.
